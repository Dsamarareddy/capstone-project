# AI Engineering Specification: Governance & Security Standards

## 1. Purpose
Define the security, compliance, and review standards applied uniformly across every application on the
platform, so security posture doesn't depend on which team built the service.

## 2. Code Review & Ownership
- `.github/CODEOWNERS` maps `infrastructure/**` and `.github/workflows/**` to the platform-owner group; `app/**`
  to the owning application team. Changes to shared platform assets always require platform-owner review.
- `.github/PULL_REQUEST_TEMPLATE.md` requires every PR to state: what changed, why, how it was tested, and
  whether it touches security-sensitive surfaces (auth, IAM, secrets, network).
- Recommended branch protection (documented here since no shared GitHub org exists yet for this capstone to
  configure live): require PR review, require the `ci` and `security-scan` status checks to pass, require
  branches to be up to date before merge, disallow force-push to `main`.

## 3. Security Gates (enforced in CI via `reusable-security-scan.yml`)
| Tool | Target | Gate |
|---|---|---|
| Gitleaks | full repo diff | fail on any detected secret |
| Trivy (fs mode) | `app/**` dependencies | fail on CRITICAL/HIGH CVE |
| Trivy (image mode) | built container image | fail on CRITICAL/HIGH CVE |
| Checkov | `infrastructure/**` | fail on HIGH/CRITICAL misconfiguration |

Findings that are accepted risk MUST be suppressed with an inline, reasoned skip
(`#checkov:skip=<ID>:<reason>` / `.trivyignore` entry with a comment), never by disabling the scan step.

## 4. Secrets Management
- No secret ever committed to git (enforced by Gitleaks in CI and `git-secrets`-style local hook guidance in
  `developer-experience-spec.md`).
- Application secrets (DB credentials) are provisioned via `aws_secretsmanager_secret` from the
  `rds-postgres` module, not environment variables baked into images.
- Local development uses `.env` (gitignored) seeded from `.env.example`.

## 5. Compliance & Documentation
- Every architecturally significant decision is recorded as an ADR (Context, Problem, Decision, Alternatives,
  Trade-offs, Consequences, Rationale) in `docs/engineering-decisions/`.
- `SECURITY.md` at repo root defines how to report a vulnerability and the supported scope.
- Container images run as a non-root user (enforced by Dockerfile review + Trivy config checks).

## 6. Versioning & Change Management for Shared Assets
- Terraform modules and reusable workflows are versioned by git tag (e.g. `modules/v1.0.0`). Consuming teams
  pin a `ref`; a breaking change to a module requires a major version bump and a changelog entry in the
  module's own `README.md`.
- Deprecation policy: a shared asset marked deprecated must remain functional for at least one minor version
  cycle before removal, with a migration note in its README.

## 7. Requirements
- R1: Every PR touching `app/**`, `infrastructure/**`, or `.github/workflows/**` MUST pass CI + security scan
  checks before merge — no bypass.
- R2: IAM roles generated by `iam-app-role` MUST be reviewed against least-privilege at PR time (CODEOWNERS
  routes these PRs to the platform-owner group).
- R3: Dependency and base-image versions MUST be pinned (no floating `latest`/`*` ranges) to keep vulnerability
  scans meaningful and reproducible.

## 8. Acceptance Criteria
- [ ] `CODEOWNERS`, `PULL_REQUEST_TEMPLATE.md`, and `SECURITY.md` exist and match this spec.
- [ ] `reusable-security-scan.yml` implements all four gates in the table above.
- [ ] At least one ADR documents the security tool choice (Trivy/Checkov/Gitleaks) with alternatives
      considered.
